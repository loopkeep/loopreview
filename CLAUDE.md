# loopreview

A review-first diff TUI — a Rust workspace building the `loopreview` and `lr`
binaries. Released: v0.1.0. This file is the working contract for any Claude
session in this repository; the README explains the product, the design, and the
features.

## Language

Everything committed here is in English: commit messages, code comments, docs,
issue and PR text, release notes, and UI strings. This is a public repository —
do not add Japanese (or any other language) to anything that lands in the repo.

## Commits

Conventional Commits — `type(scope): subject`.

- Types, as used here: `feat`, `fix`, `perf`, `docs`, `test`, `refactor`,
  `chore`, `ci`.
- Scope is the area touched: `cli`, `ui`, `github`, `markdown`, `control`,
  `core`, `pr`, `readme`, `changelog`, …
- Subject: English, imperative, lowercase first word, describing the
  **user-visible behavior** — not the mechanics.
- Mark a breaking change with `!` (e.g. `feat(cli)!: …`).
- One logical change per commit.

Load-bearing: `CHANGELOG.md` and every GitHub Release's notes are generated by
git-cliff **from commit messages**. A `feat` / `fix` / `perf` / `docs` subject
becomes a changelog line verbatim — write it as a sentence a user will read, not
an internal note.

## Gates (before every push)

`cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, and
`cargo test --workspace` all green. Then push, and confirm arrival with
`git ls-remote origin main` (local HEAD must match). If `origin/main` has moved,
`git fetch` and rebase onto it before pushing.

Reporting: never claim "pushed" or "green" from memory — ground it in the actual
command output you just saw.

## Tests

No test starts a real process. The browser opener is injected, and its real path
panics in `#[cfg(test)]` builds so a missing injection fails the suite instead of
opening a browser; git runs against local fixtures; `gh` is mocked. New tests
follow the same rule.

## Code comments

Default: write none. The code already says what it does; a comment earns its
place only by recording a **project-specific fact the code cannot show**. Five
kinds qualify:

- a hidden constraint — something that breaks if changed, not visible locally;
- an external-spec quirk — how `gh` / the GitHub API, git, or the terminal
  actually behaves;
- a workaround — why a non-obvious path is taken;
- a past incident — a bug this shape exists to prevent from recurring;
- an invariant — a property the surrounding code must keep.

No pointers. State the fact in the comment itself — never point at an issue
number (`#N`), a README / SKILL / CHANGELOG section, or a past commit hash.
(Filing GitHub Issues stays required — just never point at them *from code*.)

Before writing one, all five must hold; if any is "no", don't write it:

1. Can you name the specific change this comment forbids?
2. Is the fact absent from the code itself (not restating what the line does)?
3. Is it one of the five kinds above?
4. Would a capable colleague get it wrong without the comment?
5. Is this the only place the fact is stated?

Write it as the sentence you'd say to the colleague beside you — one or two
sentences, no preamble.

Never write: section dividers, tombstones (what used to be here / what changed),
file overviews, explanations of the language or a common idiom, doc comments that
only restate a type, or `TODO` / `FIXME` (open a GitHub Issue instead).

State each fact once, in the one place it belongs — not on every caller.

Before committing, for each comment answer (a) which of the five kinds it is and
(b) the exact change it forbids. If you can't answer both, delete it.

This applies to code you add or touch — don't sweep the file — and to tests and
config (CI YAML, `Cargo.toml`) as well.

Two examples, bad → good:

```rust
// bad — restates the call and points elsewhere
// fetch the review comments (see #42)
let all = self.fetch_review_comments(pr, review_id)?;

// good — an external-spec quirk the code cannot show
// GET /pulls/{n}/reviews/{id}/comments returns line/side as null, so the
// (path, side, line) match never reconciles — read them back through
// /pulls/{n}/comments filtered by review id instead.
let all = self.fetch_review_comments(pr, review_id)?;
```

```rust
// bad — a tombstone narrating the obvious
// used to spawn the browser here; now guarded
fn open_url(url: &str) -> io::Result<()> { … }

// good — an invariant a future test author must not break
// The real launcher is compiled out of test builds; a click test that forgets
// to inject a recording opener must fail loudly here, not open a browser.
#[cfg(test)]
fn test_opener_guard(url: &str) -> io::Result<()> { … }
```

## Docs

Keep the documentation homes fixed; do not add new ones.

- `README.md` — for users.
- `SKILL.md` (under `skills/loopreview/`) — for agents; mirrored to the public
  skills repo on a release tag.
- `CHANGELOG.md` — git-cliff–generated; never hand-edit except the hand-written
  `0.1.0` block in `cliff.toml`'s footer.
- `RELEASING.md` — the release ritual.

Unfinished work goes to GitHub Issues. Do not add standing documents or commit
progress snapshots.

## Architecture boundaries

`loopreview-core` and `loopreview-control` stay UI-free and publishable. A plain
diff uses `git` only; pull-request and issue features go through the `gh` CLI
only — never call GitHub's HTTP API directly, and never handle a token.

## Dependencies

When adding one, check crates.io for the current stable version (prefer
`cargo add`), declare it in `[workspace.dependencies]`, and commit `Cargo.lock`.

## Releasing

Bump the version only in a dedicated release commit. A `v*` tag builds the
Release and mirrors the skill; regenerate `CHANGELOG.md` before tagging. See
[RELEASING.md](RELEASING.md) for the full ritual.
